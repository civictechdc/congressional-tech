## How this was checked

- One commit implements all seven: f2fea711 (Oct 22 20:16), 86 files, +13,209 lines. Ticket files were *created* already marked `status: closed` in that same commit. Created 18:40–18:42 and closed 20:16, they carry no Notes or verification record. The docspec-rs side is 9547fed (Oct 22 20:15).
- Later changes that touch this work: 48137619 (Oct 22 22:52, ct-2ukk) moved capture storage back to the legacy schema. docspec-rs f1043af (Oct 23 00:50, ss-cnsn) removed the row-group clamp from 9547fed.
- Read-only measurements, all with scripts in scratch-syem/:
  - `syem-4t6s-probe.py` profiles the local committee-explorer release 56c87f8a (pipeline-data ceb9bbb2, committed Oct 24 05:46), which is post-f2fea711 output.
  - `syem-4t6s-prev-probe.py` re-derives the audit's problem numbers from the pre-change release ca4748be (pipeline-data e35c1853, extracted from git into syem-prev-release/).
  - `syem-4t6s-weekly-probe.py` runs the production weekly row-builder iterators over real local pipeline-data.
  - Inline pyarrow checks read the Oct 20 adoption inputs at `congressional-tech/output/incremental-updates-20261019/adoption-inputs/` (filenames, documents, state, captures).
  - A 1-row call of `prepare_capture_table` → `capture_table` checks the capture write path.
- Evidence check for the epic: `parquet-output-tables-audit.md`, cited by ct-4t6s, is not committed anywhere. I searched both repos, git history, ~/.claude projects and /private/tmp. The numbers exist only in ticket prose, but they **reproduce when re-derived**:
  - Browser sources: 308,516 rows; 1,207 RGs; retained_sha256 100% null; max cell 24,452,625 B on id d2dc516a. 74,759 duplicates over 233,757 unique, split youtube 67,242 / congress.gov 7,298 / senate.committees 124 / gpo-video-matches 72 / curated-recordings 22. 20,215 orphans.
  - Derived columns: committee_ids==[id] 3,432/3,432; meeting_id==id 18,453/18,453; witnesses.search_text derivable 66,565/66,565; issue_count==0 248,101/248,101.
  - Catalog footers: filenames 1,644 RG × 406 cols with an 81,315,147 B footer; documents 1,213 × 409 with 62,245,651 B.
  - body_key equals the template on 1,272,318/1,272,318 state rows and 2,867,269/2,867,269 capture rows.
  - Two exceptions: the sources footer total is 2.45 MB, not the claimed 2.90 MB. The stored_sha256 premise is **false**: on 0 of 2,867,269 non-null capture rows does it equal sha256, because it is the digest of the gzip object (raw_storage.py:274).
- What these checks cannot see:
  - Anything published on R2: catalog, readings, review/rows and the live raw archive.
  - The docspec workspace contents in CI.
  - Whether release 56c87f8a was ever deployed.

## Cross-cutting

- **Real evidence, rushed delivery.** The problem statements are unusually well measured and reproduce byte-for-byte. The delivery is the weak part: one commit, self-closing tickets, no committed measurement against any numeric AC.
- **Reuse failure.** Four new hand-rolled CAS body writers and a duplicate URL helper (`savedOriginalUrl` vs `savedCopyHref`), all ignoring `raw_storage.put_body`, `physical_body_object_key` and `RetainedContent`.
- **Gaps "fixed" by fabrication.** Constant timestamps, outcome `present`, congress 118, and the stored_sha256 back-fill. Each makes a non-null check pass while making the data wrong.
- **Tests that test themselves.** tests/e2e (31 files, 354 tests) runs in the default lane. 15 files import no production module, and the tier4 "real-world" tests skip in CI (conftest.py:58-65) while re-implementing the logic locally.
- Out of slice, noted only: raw_storage.py:654-672 (ct-2ukk) branches on `PYTEST_CURRENT_TEST` and reads a hardcoded relative path `output/incremental-updates-20261019/adoption-inputs/state.parquet`, swallowing all exceptions.
