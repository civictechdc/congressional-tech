# Review-9 data validation (independent re-derivation)

All numbers come from my own scripts (`v9d_*.py` in this folder), run with the ct-viewer-publish venv (`python -I`). Inputs were read-only: the receipt mirror (2,289 gzip JSONL files, 2,596,054 lines) and the pinned adoption-inputs snapshot. Method: one multiprocessing walk of every JSON value in every line (`v9d_scan.py`), plus targeted passes (`v9d_paths.py`, `v9d_cookie_odd.py`, `v9d_stored.py`). PDF populations were built from per-capture rows taken from the receipts, joined in duckdb to the index and the legacy readings (`v9d_pdf.py`, `v9d_pdf2.py`). No values were printed.

## Details worth acting on
- **Header names.** Matching on the exact name `set-cookie` misses `x-archive-orig-set-cookie`. B0's pattern needs a suffix match (`*set-cookie`). Values of `x-cache-reason: set-cookie` and `access-control-expose-headers` merely name the header; they are not cookies.
- **Embedded `/home/` hits are not local paths.** All 160 are URL paths inside "with url:" error text. Treating them as local would over-cut.
- **The plan's 117 GB** is stored bytes; Opus's 129 GB is content bytes. Both describe the same 3,061 PDFs. The plan's 3,104 adds 43 PDFs whose only capture result is `invalid_document`.
- **SR-1's "these come from the receipts"** is true for only 65% of bodies. A size check against `stored_bytes` must source the senate-captions embedded bodies from the index.

## Scores (accuracy on these claims)
- **Opus: 80.** Most numbers reproduce exactly. Deductions: it compared the plan's stored-byte GB with its own content-byte GB and missed the 43 invalid_document PDFs; it said "stopped" for what was a one-time import; it said stored values come from the receipts when 35% do not; and it missed `x-archive-orig-set-cookie`.
- **Codex: 70.** Its one measured figure (6,966 path keys) is within 0.2% of mine, and it reported 3,104 and 15,475 from the plan. It missed the second cookie shape entirely, the larger raw-safety gap.
