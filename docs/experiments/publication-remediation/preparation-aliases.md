# Bounded alias and recovery-index working state

Local bounded evidence, 2026-10-18. No acquisition, production rebuild or remote publication ran.

`AliasIndex` uses disposable SQLite tables for candidate destinations, saved-original precedence, retained body versions, accepted mappings and source/group matching. The source Parquet is scanned once; dependent SQL queries keep all invalid/self destinations as conflict evidence, refuse ambiguous targets/body versions, retain accepted and saved-original precedence, and produce the same stable ordering. Group positions use a read-only mmap rather than a Python list of every uint32 value. Input hashes remain mandatory unless an issued exact-file inventory proof applies.

Memory policy: SQLite cache requests 8 MiB and temporary SQL state spills to files. Input batches are at most 128 rows and report their Arrow bytes; this row limit is not a decoded-byte ceiling, which belongs to the separate decoded-memory ticket. Returned status arrays necessarily occupy memory proportional to the output. Preparation accounts exact publisher-encoded recovery/source/group entries against a 32 MiB output budget. It adds the encoded empty-array header and removes the final separator for each nonempty array to check the exact complete status size before success. Empty, multiple-entry and Unicode cases match the publisher byte count. It refuses rather than returning a partial status. The output budget is not a claim that Python objects or SQLite native allocations occupy only 32 MiB. Failure retains the owned SQLite directory with an exception note; success removes that scratch after closing the reader and connection.

The 18,001-source fixture includes 12,000 distinct original URLs, 6,001 body versions and high fanout to a shared destination. Instrumented Parquet iterators counted three source scans before and one after. Both paths emitted exactly 3,435,461 bytes with SHA-256 `c4216921fd737387af0d0604508a887ca17b97a856dfc2e25a75cccf91cb8e96` (see the machine receipt for the authoritative digest).

The measured Python peak decreased from 15,477,832 to 9,530,369 bytes. Process peak RSS was 134,168,576 versus 130,514,944 bytes, a fixture observation rather than a general resident-memory guarantee. SQLite scratch was 5,488,640 bytes. Runtime increased from 0.924 to 1.618 seconds. The design trades scratch and time for bounded intermediate state and fewer Parquet scans; it does not claim a production speed improvement or identify the historical OOM stage.

Validation: 101 alias/recovery/publication/transfer/workflow tests and two subtests passed. A 68-test run includes invalid/self/null conflicts, high-cardinality/fanout exact mapping, output-budget refusal and the entire review-catalog test file after its fixture correction. The final 42-test alias/recovery run includes exact full-status budget boundaries and empty/Unicode cases. Existing tests retain ambiguous bodies, failed saved responses, wrapper handling, accepted precedence, source/group counts, input hashes and publication/resume behavior. `scripts/measure_alias_preparation.py` and `evidence/preparation-aliases.json` preserve the comparison and actual scan counters.

Followups requested during independent review are included: `ReviewSelection` documents its unchanged owned-row lifetime, and the resource measurement script converts Linux `ru_maxrss` KiB to bytes while preserving macOS byte units.

The comparison preinitializes modules for both implementations before timing/tracemalloc: the original code imports saved-response helpers eagerly and the SQLite index imports them lazily. Process RSS still includes initialization. Exact header accounting took 0.000087 seconds in the final traced fixture and introduces neither a second full JSON walk nor a full encoded status copy. Entry formatting remains part of the measured preparation time.
