# File custody and streamed catalog verification

The original hard-link test failed because removing an alias can leave `st_ctime_ns` unchanged within one Linux filesystem clock tick. A separate 30-iteration probe accepted the old proof after 29 removals while `st_nlink` changed from 2 to 1. Commit `317e0989` adds the link count to the existing process-local custody identity, preserving device, inode, size, modification time, change time, process, path and issued-object checks. Deterministic regressions cover both adding and removing a link with unchanged timestamps.

A separate source-content gap remains possible with metadata alone: a same-size rewrite can retain both timestamps. A deterministic regression reproduced catalog upload of changed bytes using the old expected SHA-256. `R2Store.put_derived_file` now computes actual SHA-256 alongside MD5 in its existing bounded read and compares it with the expected digest before PUT. This adds no file-read pass. The regression checks that a stale digest produces zero PUTs. Existing transport tests verify MD5 and byte counts, while a counted reader confirms one checksum scan followed by the service consuming the upload.

The focused shared-helper, catalog-file, R2-body, transfer and viewer-inventory checks passed on macOS (75 tests and 2 subtests) and isolated Linux ARM64 (75 tests and 2 subtests). These runs did not use release data, credentials or a live publication container.

A bounded warm-cache measurement used a synthetic 128 MiB file, one Linux ARM64 CPU and three scans per arm. Median MD5-only time was 0.266171 seconds; MD5 plus SHA-256 in the same read took 0.315908 seconds; SHA-256 alone took 0.078364 seconds. The shared scan adds about 0.050 seconds per sampled 128 MiB. This measures checksum CPU/read cost, not cold-cache, network or end-to-end publication performance.

The general `VerifiedFile.require` implementation still checks observed metadata rather than rereading content. `GuardedPublicationClient` can likewise use the cached digest when issuing a receipt after an acknowledged upload. Those separate paths require correction before claiming that all successful proof checks establish unchanged bytes. A content-hashing fallback in `require` is straightforward but adds one full file-read pass per successful call; hashing a counted upload stream can validate its receipt without another read. Neither filesystem clock delays nor fixture timestamp changes establish byte identity.
