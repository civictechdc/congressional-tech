# File custody and streamed catalog verification

The original hard-link test failed because removing an alias can leave `st_ctime_ns` unchanged within one Linux filesystem clock tick. A separate 30-iteration probe accepted the old proof after 29 removals while `st_nlink` changed from 2 to 1. Commit `317e0989` adds the link count to the existing process-local custody identity, preserving device, inode, size, modification time, change time, process, path and issued-object checks. Deterministic regressions cover both adding and removing a link with unchanged timestamps.

A separate source-content gap remains possible with metadata alone: a same-size rewrite can retain both timestamps. A deterministic regression reproduced catalog upload of changed bytes using the old expected SHA-256. `R2Store.put_derived_file` now computes actual SHA-256 alongside MD5 in its existing bounded read and compares it with the expected digest before PUT. This adds no file-read pass. The regression checks that a stale digest produces zero PUTs. Existing transport tests verify MD5 and byte counts, while a counted reader confirms one checksum scan followed by the service consuming the upload.

The focused shared-helper, catalog-file, R2-body, transfer and viewer-inventory checks passed on macOS (75 tests and 2 subtests) and isolated Linux ARM64 (75 tests and 2 subtests). These runs did not use release data, credentials or a live publication container.

A bounded warm-cache measurement used a synthetic 128 MiB file, one Linux ARM64 CPU and three scans per arm. Median MD5-only time was 0.266171 seconds; MD5 plus SHA-256 in the same read took 0.315908 seconds; SHA-256 alone took 0.078364 seconds. The shared scan adds about 0.050 seconds per sampled 128 MiB. This measures checksum CPU/read cost, not cold-cache, network or end-to-end publication performance.

The shared verifier correction (`da3c4d4a`) makes `VerifiedFile.require` check the current digest through the maintained `verify_local_file` primitive after checking its authority and metadata. It rejects both same-metadata content replacement and a constructor-supplied unchecked digest. General successful calls now add one bounded full-file read. The existing metadata-only check is internal and used only at transport boundaries that independently hash the consumed bytes. The shared-verifier, catalog and inventory regressions passed on macOS and Linux (55 tests each).

Both maintained viewer upload clients now hash and count the sequential bytes consumed by the SDK, checking them before a verified receipt or successful-write callback is issued. The stream check handles SDK probe/rewind and `readinto`; stale expected bytes and short acknowledged reads fail. Issued proofs can use this actual transport scan without a separate preflight read. A real boto3 conditional PUT against a fixture-only loopback HTTP server exercises SDK checksum and rewind behavior. Successful responses still require no remote readback; uncertain outcomes keep the existing remote reconciliation path and write conditions.

The pre-final broad macOS regression set passed 197 tests and 2 subtests; the separate real SDK check passed. The analogous Linux run passed 196 tests and 2 subtests but failed two existing release-source-cache tests on same-tick content edits; those are outside the viewer stream patch. Final targeted stream checks passed on both macOS and Linux (32 tests and 2 subtests each), including the real SDK canary, stale proofs with identical metadata and an exact one-read budget for issued-proof uploads. The two source-cache failures must remain visible for integration qualification. No live release container, credentials, R2 data, or public pointer was changed by this work.
