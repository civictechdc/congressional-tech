## Data flow and invariants

1. **Inputs remain the original inputs.** `attempt.prepare` creates the source, viewer, accepted-recovery, code/runtime, revision and native-execution binding at `attempt.py:53-90`. Resume substitutes only the origin's run/attempt fields (`:92-97`). `Continuation` compares the whole binding (`continuation.py:145-148`). The renderer independently compares source, requirements, reviews, prior v5 review binding and the preparation binding (`filename_native.py:936-944`; `filename_renderer_state.py:58-67`). Changed controls/config/reviews therefore cannot silently inherit completed tasks.
2. **Completed work is distinct from incomplete work.** `RendererState.run` stores results and commits before emitting completion (`filename_renderer_state.py:180-189`). Before-completion interruption rolls back that task, while prior committed chunk tasks survive. Each asset's path, size and hash is checked on restore (`:78-147`). Source/physical-chunk task identities are created by the real callers (`filename_native.py:332-336`, `:545-549`).
3. **Saved files remain quiescent while hashed.** The supervisor removes child `GITHUB_OUTPUT`, waits for process exit, rejects forced shutdown and probes the process group before calling the checkpoint saver (`W:106-148`). The workflow uploads the entire checkpoint tree with hidden files enabled (`.github/workflows/publish-filename-viewer.yml:178-188`). The receiver checks the receipt hash/name and every file before invoking runtime preparation (`resume.py:174-189`; `W:101-105`). F2 limits direct branch-test evidence, not the static order.
4. **Artifact producer can change without changing origin.** Incomplete preparation retains `binding.run_id/run_attempt`; the completing run writes `artifact_producer` and the accepted name (`attempt.py:170-208`). A receipt without a result may take the new producer, preserving its release plan; a complete pair keeps its existing identity. Legacy receipts fall back to their origin (`:179-188`, `:239-248`). GitHub custody checks that producer at publication (`:325-330`).
5. **Checkpoint custody does not authorize publication.** v2 is accepted only with `allow_preparation=True` (`resume.py:22-24`). A complete pair cannot be saved or consumed as incomplete (`:110-116`); CLI publish rejects v2 before client creation (`publication_cli.py:64-71`). A bounded-stop complete pair passes the real complete verifier and current-producer gate (`W:71-89`). The workflow has disjoint checkpoint and accepted upload/publish conditions (`.github/workflows/publish-filename-viewer.yml:178-242`).
6. **Original revision is explicit.** The receiver binds actual checkout, descriptor revision, producer workflow revision and producer repository (`resume.py:163-177`). v2 dispatch additionally requires `GITHUB_SHA == descriptor.revision` (`W:31-32`, `:64-65`), preventing a later accepted v1 descriptor from falsely claiming the run's newer workflow head as its effective source. A newly changed runtime/config correctly requires a fresh preparation.
7. **A stopped whole recovery stage can repeat.** Recovery is outside the renderer state (`native.py:110-128`), so an interrupted recovery scan restarts while finished rendering is reused. Once the prepared phase exists, `attempt.prepare` verifies and returns its inventory instead of invoking rendering/recovery (`attempt.py:154-161`). This is existing explicit behavior, not a per-row recovery guarantee.
