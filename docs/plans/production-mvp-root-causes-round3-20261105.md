## Findings that change the diagnosis

### Recovery has two distinct writer defects

In [ReceiptWriter](../../packages/congress_api/src/congress_api/retention/receipt_writer.py), `write()` sends an existing frozen checkpoint directly to `_apply_frozen()`. That method verifies its bytes and attempt identity, then uploads it without calling `refuse_local_paths`. The maintained recovery importer reaches this branch. A validly pinned old checkpoint can therefore bypass the fresh-write check for an absolute nested local path. No leaking checkpoint or new live exposure was established. The smallest fix is the same refusal before upload, outside the lost-acknowledgment handler, while preserving safe frozen bytes and idempotent retries.

[BodyStore](../../packages/congress_api/src/congress_api/retention/body_store.py) has a separate reuse problem. Cache, retained-reference and legacy-object paths discard storage metadata; a create-only upload refused because the object already exists also returns no observed replacement metadata. The receipt writer emits those fields only for a newly stored outcome. An attempted compressed upload's digest and length cannot stand in for the existing object's values.

Preserve previously verified cache metadata, reuse metadata from an exact-key lookup already made, and perform one metadata lookup only where the existing object remains unqualified. Keep the outcome `unchanged`. The capture parser already accepts the fields, so a parser change and broad replay are not indicated. The earlier 85-body incident involved present but unpinned objects; the delivered reader fallback and e145 publication already mitigate that cohort.

The recovery-note ticket, `ct-nh41`, is smaller. The reconciler still writes pipeline boilerplate into a field intended to explain the relationship to the original. Published e145 already removes the exact boilerplate: 10,772 notes were filtered, and all 12,618 published notes are null. Fix new authoring on the next recovery change, preserve real explanations and relationship kinds, and reuse the exact legacy filter. If historical decisions need correction, use the existing append/supersede path with a new identity; changing note text under an existing immutable decision ID is not a safe update. No body replay is needed.

### Scheduled acquisition and raw protection need specific operational reconciliation

The capture workflow was **disabled manually with zero recorded runs** when read on November 5. The visible repository settings and environments do not establish the required enable flag, pointer and budgets. Organization settings returned a permission refusal, so effective inherited values remain **unknown**. The published e145 manifest and engine pin agree, but the restored Mac publisher and the GitHub acquisition workflow perform different jobs.

The current capture command supplies neither a cutoff URL list nor the weekly seed inventories described in its documentation. Its actual starting queue comes from the selected release's URL state, with further discovery during the run. Correct the documentation or explicitly bind a needed input; do not restore obsolete seed machinery by default. Also preserve nested failure summaries in the workflow's uploaded results. A failure after remote receipt acknowledgment but before the local completion marker can omit that receipt from the summary. This is a demonstrated accounting mechanism, not demonstrated loss of the stored receipt.

For raw protection, three exact-key metadata reads match the **pre-cleanup** receipt sizes and ETags, with modification dates preceding the October 30 completion note. They contradict a blanket claim that the B0 rewrite completed for those keys. They do not establish the state of all other receipts or reveal their contents. The later owner exception allows retained historical paths; it does not by itself resolve any separate header-cleanup obligation.

Current bucket lock settings could not be read with the available object credentials. Their state remains **unverified**, rather than assumed absent. Reconcile the three counterexamples and owner dispositions, then obtain the bucket policy readback through its existing owner. Preserve the historical-path exception. This audit gives no reason to rerun the old cleanup over raw history.

### Performance work is useful, but the latest release already fits

The latest qualified build completed in **513.2 seconds**, with **9.981 GiB peak resident memory** and **9.389 GiB peak physical footprint**, under its 14 GiB watchdog limit. Approximate alignment of retained samples places the physical peak during capture-evidence export. The resident-memory peak occurs later; those measurements are not interchangeable.

The next useful candidate is the already studied bounded export sort, if a feature or runner has a measured headroom problem. Retained one-partition probes succeeded from 0.25 GiB upward; the proposed implementation uses a 512 MiB per-export cap. The older report's roughly 1 GiB floor partly measured the probe's own shuffle. Probe equivalence and spill results are reusable, but integrated savings remain unverified. Preserve output ordering and identity, qualify one candidate, and measure the new bottleneck before further SQL changes.

One equivalent `body-admissions.sql` rewrite also changed the byte-hashed readings bundle. Although the compared SQL results agreed, **24 sniff failures and one page failure** ceased to count as settled. The planted wrong-value comparison detected 42,395 differences, strengthening the diagnosis that version selection caused this particular failure. Restoring the original bytes repaired it.

`ct-zpbl` addresses the underlying coupling. Honor its declared-version and advisory-warning policy. A warning does not establish semantic equivalence: a missed bump can keep stale rows eligible while new bodies receive changed values under the same version. Existing `lock_only` compatibility still admits an older sniff version. Keeping current declared stamps alone does not preserve those rows if that selector is deleted. Compare selected logical rows and pending work before retiring compatibility machinery; no raw-body replay is needed merely to compare selection.

### Some apparent gaps are evidence or scope problems

`ct-syem` asks for a UTC day-boundary case and refusal of timezone-less input through an affected caller. Existing [YouTube tests](../../packages/youtube_api/tests/test_youtube_interpretation.py) assert both, including conversion from December 31 at 23:00 −05:00 to January 1 at 04:00 UTC. [Transcript tests](../../packages/congress_api/tests/test_congress_api_transcripts_refactor.py) also cover offsets, daylight-saving transitions and unzoned input. The audit overlooked them by searching for direct helper tests. Credit these assertions; do not invent a new unit-test obligation. Their current execution was not rerun. Any remaining execution check can follow the existing next-parser-change deferral.

For `ct-31e2`, the original MCP fixes passed in [hosted run 41368448887](https://github.com/civictechdc/congressional-tech/actions/runs/41368448887), including 66 native producer tests and two standard-input/output consumer tests. The corresponding Explorer run passed six offline shards, then exposed a site-build ordering problem. Commit `98eec583` repairs that order. Later probe runs stopped at runtime revision admission before reaching loopback, so they neither prove nor disprove the repaired loopback. Retain the completed checks and obtain the missing result with the next relevant, correctly configured hosted run.

The remaining House maintenance is narrow: `ct-8bzh` gives child correctness checks a load-sensitive 10-second deadline, while `ct-a3le` has two diagnostic tests dynamically importing a research script. Preserve real CLI and corruption checks, make their timeout a measured hang guard, and move the single maintained diagnostic to an importable owner. Neither requires parser semantics changes or a broader News Lake migration.

## Practical sequence and ticket implications

1. **Continue the first-round feature repairs.** This batch adds no reason to make full migration, canonical names or a versioning redesign prerequisites for a shareable research product.
2. **Repair writer reuse when enabling the affected recovery path.** Keep `ct-f9hw` and `ct-m56x` separately actionable: their failure mechanisms and checks differ. Share bounded fixtures where useful. Fix recovery-note authoring with the next reconciliation change.
3. **Treat ongoing freshness as acquisition plus publication.** `ct-4jms` supplies sources; `ct-ud0b` from round two publishes qualifying changes and resumes completed work. Preserve that ownership distinction. Resolve raw-lock evidence with its owner.
4. **Shrink maintenance to the demonstrated gap.** `ct-syem` is a strong candidate for evidence reconciliation rather than more code. `ct-31e2` needs the remaining hosted boundary, not repetition of all passed tests. Keep the House work narrow and canonical-table migration conditional.
5. **Reuse the existing performance experiments when capacity requires them.** Avoid another unbounded Git repack: the retained attempt exceeded its memory limit, and current pack size does not establish reclaimable space. Verify sample custody before eliminating proof copies.
