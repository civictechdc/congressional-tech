## 1. Introduction

The specifications define components and their contracts; implementations are injected behind them (principle 8). Today's code was built by trial and error, so it holds both hard-won behavior and accumulated over-engineering. Binding separates the two:

- **Bind:** the existing code already meets the contract; it moves behind the component as is.
- **Adapt:** the existing code does most of the job; the listed changes close the gap.
- **Build:** nothing today fits; the component is new.
- **Seed:** the code is not bound, but the behavior it learned becomes registry entries, parser rules or fixtures (§4).

Every binding is proven by the component's contract test, never by the old code's own tests.

## 2. Binding Rules

These rules come from what went wrong and what grew too large in today's code ([[INVENTORY]] §6.1, §6.3).

1. **One implementation per component.** Today has five raw write entry points, each with its own `immutable` flag and its own handling of an existing object. The body store binds one and the others are deleted.
2. **Adapters only at external systems.** The object store and local disk, the direct and provider transports, and the catalog are injected adapters. Nothing else varies by environment.
3. **Tests inject adapters; production never branches for tests.** Today's code carries 75 test-only branches and local-file substitutions on raw paths, and the engine has fast paths keyed on dataset names. None is bound; the ratchet (A §15.7) keeps them out.
4. **Policy is data.** Every list a rule needs is a registry or a profile version. A component that hard-codes a host, an error word or a URL pattern is adapted before it is bound.
5. **Platform primitives replace bookkeeping.** Conditional writes, Content-MD5, ETags and catalog commits do what custody read-backs, journals, quarantine copies and the hand-built raw index did. None of those is bound.
6. **Raw is write-once.** No bound component defaults to deleting or overwriting. The only sanctioned rewrite is the one-time receipt cleanup (plan B0).
7. **The engine runs the data path.** Python code that duplicates what docspec-rs does or should do (merges, URL resolution, hashing in custody paths) is not bound ([[INVENTORY]] §5.3).
8. **Dormant code gets a use or a reason before it goes** ([[INVENTORY]] §5.4).
