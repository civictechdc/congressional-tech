## 1. Introduction

The specifications define components and their contracts; implementations are injected behind them (principle 8). Today's code was built by trial and error, so it holds both hard-won behavior and accumulated over-engineering. Binding separates the two:

- **Bind:** the existing code already meets the contract and moves behind the component as is.
- **Adapt:** the existing code does part of the job; the listed changes close the gap.
- **Build:** nothing today fits; the component is new.
- **Seed:** the code is not bound, but the behavior it learned becomes registry entries, parser rules or fixtures (§4).

Every component is proven by its contract suite, written from the specification. Cases from today's tests are lifted into that suite; the old tests themselves prove nothing about the target.

## 2. Binding Rules

Principles 3, 5 and 8 and [[ARCHITECTURE]] §15, item 7 govern every binding. Three rules from what went wrong in today's code ([[INVENTORY]] §6.1, §6.3) apply on top of them:

1. **One implementation per component.** Today has nine raw write entry points, each with its own handling of an existing object; the body store binds one.
2. **No component defaults to deleting or overwriting raw data.** The one sanctioned rewrite is the one-time receipt cleanup, done by its own tool (plan B0).
3. **Dormant code gets a use or a documented reason before it goes** (§5).
