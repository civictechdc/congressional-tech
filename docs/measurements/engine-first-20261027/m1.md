## Decision and controlled conditions

Run on an otherwise idle `ubuntu-24.04` runner with four CPUs and 14–16 GiB visible RAM. Use the standard optimized Cargo `--release` build; remote execution refuses debug builds and report admission requires `release_build: true`. Pin one compiled probe for all arms; each report records its BLAKE3, table UUID, writer profile and workload. DataFusion uses four target partitions, a 10 GiB spill pool and 32 GiB scratch ceiling. The native Iceberg static provider has its own scan implementation and uses host CPU concurrency; its allocations are not all charged to DataFusion's pool. Record process peak RSS, free space and actual runner resources, and refuse to qualify an out-of-budget experiment. Do not substitute a Mac timing.

The workload uses `(day, item)` as identifier fields, partitions by day, and includes a deterministic string payload. The default 15,000 rows approximate the plan's small day-sized append; actual bytes are reported. Every observation checks the exact key grid and payload. Its timed scan streams **all columns**, rather than using a count that could be answered from metadata. Separate validation scans are outside that timing. Listing and footer work is linear in files/objects; exact distinct-key validation can spill. Report metadata is capped at 32 MiB; split large append commands before that bound.

Use four fresh tables in one dedicated namespace: `growth`, `capped`, `uncapped`, `projected`. Growth and projected use the engine's uncapped experimental layout (128 MiB files, 65,536-row groups); capped uses 2 MiB files and 2,048-row groups. The probe calls the shared engine writer and guarded append, rather than a second writer implementation. Each table pins its row count and writer profile at creation.

The growth projection is fixed before remote measurements: for files, manifests and current data bytes, take the latest head plus 3,650 times the largest observed positive per-day increase, rounded up. Also require another 3,650 days of rows at the pinned daily volume. Ten distinct, completed Basin maintenance runs are required. The projected table must meet **all** file, manifest, byte and row targets, with the same uncapped profile and binary. This deliberately conservative method prevents qualifying a small or empty table with many tiny files.

Keep Iceberg only if rows remain unchanged and the projected full scan takes **strictly less than 60,000 ms** on the specified runner. Otherwise use PLAN's dated-Parquet fallback. Missing evidence produces `incomplete`, not a format choice. Guard/rerun evidence and an identifiable compactor-output footer must also be present.

For cap cost, use fresh `capped` and `uncapped` tables with at least three paired, equal-volume day appends. Alternate arms for both writes and scans; scan each actual committed snapshot before its next append. A changed binary, table generation, workload, snapshot or non-interleaved scan order invalidates the comparison. Keep caps only if the slowest capped trial is faster than the fastest uncapped trial for scan or commit cost; otherwise drop caps. Retain every trial. This defines “measurably help” before measurements and avoids treating timing noise as benefit.

## Prepared owner commands

Build and run from `ds-engine-first`; the executable is `target/release/examples/basin_maintenance_probe`. `M1_WORK` is a private local evidence directory; `M1_NS` must be `docspec_m1_` followed by a canonical UUID's 32 lowercase hexadecimal digits. Provide the `DOCSPEC_M1_*` environment values outside this document: bucket, catalog URI, warehouse, S3 endpoint, catalog token and scoped S3 credentials. The bucket must start `cx-engine-first-lock-probe-`; the catalog URI must end in that bucket. Never use the raw archive bucket. This experiment needs a disposable maintenance-enabled bucket, not an indefinite object lock that would defeat purge/expiration.

```sh
cargo build --release --locked --offline --all-features --example basin_maintenance_probe
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --plan --scratch "$M1_WORK/spill" --output "$M1_WORK/plan.json"
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action create --table growth --allow-scratch-writes --scratch "$M1_WORK/spill" --output "$M1_WORK/growth-create.json"
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action race --table growth --day 0 --allow-scratch-writes --scratch "$M1_WORK/spill" --output "$M1_WORK/race.json"
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action observe --table growth --day 1 --allow-scratch-writes --scratch "$M1_WORK/spill" --output "$M1_WORK/before-maintenance.json"
```

The race injects a second client immediately before catalog update; the server must reject the stale commit. It reuses already written files, recomputes the work list and actually repeats ingestion. Running it again on populated days refuses. Preserve this report for the final decision.

Enable Basin compaction and the shortest available snapshot expiration. For each of at least ten **completed** maintenance runs, append one new day and observe after maintenance. For the first, use day 2 and the initial observation; advance both on later runs:

```sh
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action append --table growth --day 2 --allow-scratch-writes --scratch "$M1_WORK/spill" --output "$M1_WORK/write-2.json"
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action observe --table growth --day 2 --allow-scratch-writes --previous-observation "$M1_WORK/before-maintenance.json" --write-records "$M1_WORK/write-2.json" --maintenance-run "$M1_RUN" --maintenance-evidence "$M1_WORK/maintenance-2.json" --scratch "$M1_WORK/spill" --output "$M1_WORK/growth-2.json"
```

Supply the actual Basin completion evidence in JSON: `source: "basin"`, `completed: true`, `run_id` equal to `M1_RUN`, and `table_uuid` equal to the growth table. Retain its upstream source with the report. An elapsed wait or a made-up run ID is not a completed maintenance run. Each observation records current files/manifests/metadata files, expired bytes, exact rows, the pushed partition predicate and a native footer. Compactor attribution requires complete successful append inventories since the previous observation; prior observations and append records must share table generation, workload and binary. No-op append reports cannot identify new files.

After ten runs, pass their paths in chronological order:

```sh
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action projection --observations "$M1_WORK"/growth-*.json --scratch "$M1_WORK/spill" --output "$M1_WORK/projection.json"
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action create --table projected --allow-scratch-writes --scratch "$M1_WORK/spill" --output "$M1_WORK/projected-create.json"
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action append --table projected --day 0 --batches "$M1_TARGET_DAYS" --allow-scratch-writes --scratch "$M1_WORK/spill" --output "$M1_WORK/projected-write.json"
target/release/examples/basin_maintenance_probe --namespace "$M1_NS" --action observe --table projected --day "$M1_LAST_DAY" --projected --projection "$M1_WORK/projection.json" --allow-scratch-writes --scratch "$M1_WORK/spill" --output "$M1_WORK/projected-scan.json"
```

Set `M1_TARGET_DAYS` from the projection, and `M1_LAST_DAY` to that value minus one. Use zero-padded report filenames or explicitly ordered arguments. If counts or bytes do not reach every projected target, add day-sized batches and observe again; retain the unsuccessful attempt. Do not treat the target flags as evidence of achieved volume.

Create both cap tables using the same `create` command with their table names. For day 0, 1 and 2, run `append` followed immediately by `observe`, adding `--cap-trial` to both commands and alternating table arms for each paired trial. Keep all write and scan JSON files. Then evaluate all growth, race, projected and cap reports:

```sh

```
