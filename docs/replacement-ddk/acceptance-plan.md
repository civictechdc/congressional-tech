# Replacement acceptance protocol

Status: incomplete acceptance, November 6, 2026. The original tiny fixture has
passed retained native requalification, DDK checking, selection and its focused
consumer cases. Current source boundaries also have focused test evidence.
These results do not close the full model, acquisition, recovery or publication
proofs below. [Status](status.json) records their exact scope and remaining work.

The migration is greenfield: all producers and readers move to the same current
catalog format. Baseline inventories retain observations about old formats, but
those observations impose no old-reader or old-controller-state compatibility
requirement. Prior-version checks below concern versions made by the new stack.
Retained source facts, exact native input access and useful valid completions
remain in scope.

## Evidence per capability

The two capability JSON files assign an owner and proposed independent executable
proof to each row. Before executing a row, bind the actual proof entry point,
independent expectation source, input snapshot/occurrences, implementation and
runtime tuple, limits, expected comparison scope, and stopping condition. After
execution, record exit status, full/partial coverage, exact output/evidence
references, unread or excluded records, and independent review. An unimplemented
proof remains `unverified`, even when the incumbent has a similarly named test.

The acceptance harness belongs to the application test suite. It may invoke real
entry points and compare outputs, but cannot import the producer to manufacture
its expectations. Raw checks also follow the repository's stricter independence
rules: different raw facts or measure, both comparison directions, every unread
record named, one planted producer-like wrong value, and nonauthor confirmation.

## Authentic evidence and scope reconciliation

Freeze distinct references for current source behavior, retained published release,
retained candidate inputs and independent expectations. Source and selected release
can differ. A newly supported field absent from an old immutable release stays an
unverified obligation; its old-release absence cannot lower the replacement scope.
Do not count existing regressions as required business behavior. Record a deliberate
repair separately and prove the intended result from source facts.

For each source family and each consumer, report expected, inspected, omitted and
unresolved populations with comparable units. Resolve the exact retained corpus
through owner manifests; do not copy all payloads to discover what exists. The
current inventories are source-grounded preparation, not a completed corpus census.

## Execution and decision

Implementation and new proof entry points begin only after the live release gate
is true. Use this worktree's environment and maintained runners. A path-filtered
pytest run remains partial; only `(full lane): exit 0` or all required shards can
establish a fully tested branch. Heavy checks use the required watchdog and a
parent-coordinated resource allocation.

A replacement capability can pass only with its expected semantics, real entry
point, exact version and required independent evidence. Missing, unknown, failed,
or not-run required proofs keep delivery incomplete. Preserve failure artifacts
and useful completions. A passing local replacement does not publish externally
or authorize production activation.
