# Enforce column projection across all 353/356-column catalog readers and verify zero unprojected core scans

Production filenames.parquet has 353 columns (348 nested list/struct columns, 1,683,430 rows, 1,644 row groups) and documents.parquet has 356 columns (351 nested, 1,241,157 rows, 1,213 row groups). On our actual-scale projection probe (probe_docspec_scale.py Probe 0), reading 4 projected key columns (source_id, document_id, source_url, body_key) vs all 353 columns took 0.0007s (1.19 MB Arrow) vs 0.0205s (38.80 MB Arrow) — a 28.78x speedup and 32.61x memory reduction. Any reader that omits columns=... on CatalogRows.read or NativeDatasets.read_keys pays a ~30x decode and memory penalty.

## Design

Audit every call site of CatalogRows.read, NativeDatasets.read_arrow, NativeDatasets.read_keys, and pq.ParquetFile.iter_batches across packages/congress_api and packages/viewer_publication. Ensure that routing, membership closure, fingerprint verification, and incremental diff passes always supply explicit columns=... projections, reserving full 353/356-column reads strictly for final changed-component materialization and full adoption qualification.

## Acceptance Criteria

- All non-materialization catalog reads in packages/congress_api and packages/viewer_publication pass explicit column projections.
- CatalogRows.read pushes root column projection down to the native stream / read_keys path rather than decoding all 353 core columns before projecting in Python.
- Add a test asserting projected byte/column counters on CatalogRows.read.
