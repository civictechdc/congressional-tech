# 34,588 GovInfo 'Content Details' landing pages are document pages beside the PDF they point to

Release-prep model output next-20261108-3ebe6872 (`detail.parquet`, 356,736 documents): 34,588 documents have a `www.govinfo.gov/app/details/CHRG-…` (also CRPT/CPRT/CDOC) page as their saved file. `record-roles.sql` gives the page role `document`, so it is a real file and gets its own document page. For every one of those packages the actual file is also saved as a separate document: 34,549 have the package PDF saved, 448 of those also the `.htm` text, and the other 39 the `.htm` only. None is missing its file, so this is not a capture gap.

The landing page carries no hearing text. Its body_text is about 4,800 characters of GovInfo navigation, share icons and script (slice sample: 2,128 such pages, .cache/archive-release/body-text-slice-20261109). It doubles each published hearing in lists and search and will add ~34,600 junk texts to the body_text export.

Likely fix: the role rule treats a GovInfo details page as a `wrapper` (a page whose job is to link to the file) when the package's file is saved, the same way download wrappers are handled (data model section 7.3; the role sample there already names 'cover-only GovInfo pages'). Keep its metadata as a source of the real document. Decide what the 39 htm-only packages do. This changes document counts and identities for one publisher, so it is a deliberate model change with a before/after count.

## Acceptance Criteria

- A GovInfo details page whose package file is saved is not a document page; it remains a source row on the real document.
- Before/after counts: documents, published-hearing documents, and the 34,588 named.
- Model invariant suites pass; no real document loses its only saved file.

What a reader gets instead needs a model step outside the role files, and a choice.

Measured on release 619db5f9e08e. Scripts and outputs: `.cache/archive-release/investigations/document-roles-20261110/` (`dr-40-roles.out`, `dr-22-m878-options.out`, `dr-23-m878-counts.out`).

What is there:

- 34,826 documents are saved at a `govinfo.gov/app/details/` address: 34,588 package pages and 238 granule pages (`/CHRG-x/CHRG-x-add1`), all CHRG, 1.38 GB of page bodies. Each is its own row with one address, no meeting, kind `published-hearing`. They are 34,826 of the release's 71,624 published-hearing documents and of its 49,498 web-page documents.
- All 34,826 link keys were already live before last night. The rows also hold 34,827 lookup keys and 34,826 addresses, none shared with another row.
- 34,340 are linked from their own package ZIP, which is how they were captured.
- The page's title is the only place the hearing number is published: "S. Hrg. 111-774 - EXAMINING THE CAUSES... - CHRG-111shrg62513 | Content Details | GovInfo" beside the document's "- EXAMINING THE CAUSES...". 136 of the hearings' own documents have no title at all.

The role rule, ready: a `wrapper_url` entry (the kind ct-aoxp added) for `^https?://(www.)?govinfo.gov/app/details/`. Run as a scratch entry with the committed SQL through the pinned engine on all 4,176,147 capture rows: exactly these 34,826 pages change from `document` to `wrapper`, and no other row. Documents 357,471 to 322,645; published hearings 71,624 to 36,798.

Which document a page stands for, by the package or granule name in its address: 33,730 pages have exactly one document so named; 968 have several (a PDF and a text that the rendition rule did not join, mostly multi-part hearings); 126 have package documents under other names only; 2 have no document of the package saved (CHRG-107hhrg72330, CHRG-108shrg86911).

Options:

1. Role rule alone. The rows go; the 34,826 keys retire with no successor and no address to list, because the details address is on no surviving row; the lookup keys and addresses go too. Smallest change, worst for a reader holding a link. Not recommended.
2. Role rule, and the page becomes another address of its hearing (recommended). A new step attaches each wrapper page to the document named for it, the way a ZIP's address stays on its contents. The address row and lookup key survive on the hearing. The link key still leaves `links`, since the page is not a body of the document, so it retires: today's address rule in retired-links.sql redirects only to an equal text fingerprint, so it would show a removal notice that lists the hearing; a redirect needs one more successor rule there (a retired wrapper's key goes to the single document at its address). Decisions: redirect or notice; which document for the 968 with several (the PDF, by format order, is the plain choice); the 126 and the 2 get a plain notice, or the 2 stay documents until their file is saved.
3. Keep the row and mark it. No flag fits: `hidden` means removed by review and shows that note. A new flag is a schema change every consumer must filter on, and the body_text export still carries 34,826 navigation texts unless it filters too.

Not an alternate: an alternate is another format of the same document, one body per format. The page holds none of the hearing's text, and 968 hearings already have an HTML rendition.

Also for the owner: whether the page's title should fill the hearing's (it carries the hearing number); and the capture scope still admits these pages, so each new package adds one.

Same shape elsewhere, not measured further: about 300 congress.gov `/bill/<congress>/...` pages are documents beside the bill texts they describe.

A full model build of option 2 must confirm: no row saved at a details address; each of the 34,826 keys in retired_links, with the successor or address list chosen above; every details address and lookup key still answering, on the hearing's row; no hearing loses its only saved file; the link rule passes with no live key, lookup key or address answering another file.
